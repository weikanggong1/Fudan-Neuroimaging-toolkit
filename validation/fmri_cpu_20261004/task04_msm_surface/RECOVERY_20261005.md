## 官方失败的判断顺序

当前已知事实是原版 command_0 返回 1、候选尚未运行；具体原因由实际 stderr 与内部 workflow 日志决定。

| 日志证据 | 核对及具体处理 |
| --- | --- |
| pinned helper SHA 不同 | 比较绑定、服务器实际 helper 和本地源码。完整 surface 绑定保存的原 helper 版本与当前 main helper 版本不同；不能直接替换 hash。新的参照 helper、绑定和 manifest 放独立目录，记录改变的代码与 SHA，保留旧结果。 |
| Singularity 失败、没有容器 worker 报告 | 读取实际命令及容器日志，分别检查引擎、SIF SHA、输入/脚本/工作目录 bind、解释器、权限和共享目录。不能把 wrapper 返回值当完成报告。 |
| setuid launcher 明确在 host strace 下失败 | 保持原 payload、输入、SIF 和 CPU 预算，取消对 host Singularity 的 strace，改用容器内子进程退出回执；这是验证入口修复，不是算法修改。当前 task04 harness 和所读参照 helper 没有使用 strace，尚无证据表明本次失败属于此类。 |
| Workbench、FreeSurfer 或 Nipype node 返回非零 | 保留原子命令、原 stderr、所有完整帧数及模板检查。仅修复确实错误的参照安装/bind/入口，不把跳过失败节点或减少数据作为 benchmark。 |
| 缺少 TemplateFlow 文件 | 按实际原版请求核对离线缓存与网格/分区 SHA；从授权原站补齐资源，另存新的完整缓存版本。不能用形状相近模板替换。 |
| `EXDEV` 或已存在输出目录 | 核对原 worker 是否确实完成、所有输出 SHA。跨文件系统发布采用校验拷贝及目标目录原子改名；新尝试使用全新输出和 work，不能通过覆盖旧失败目录继续。发布时间另列。 |
| 工作流已完成但数值/轴/几何不同 | 比较完整双侧球面、全帧 GIFTI、CIFTI 的 axes/TR、有限性和 dtype，定位第一处不同；不能只接受 process exit zero 或平均相关。 |

## 容器退出回执的复用条件

根任务的 `task05_volume/container_reference.py` 可用于记录实际 payload 的退出状态，但 task04 的容器使用命名 bind `/reference-work` 与 `/reference-script`。若复用，需要让回执明确写入容器可见的 `/reference-work/native_child_exit.private.json`，在 host 对应 work 目录读取；不能默认 host 绝对路径在容器中可见。

task04 当前 payload 用裸 `python`。该回执 helper 会读取 `argv[0]` 的二进制 SHA，复用时应改为镜像内实际、固定的绝对 Python 路径并现场核对；原 worker 脚本和参数保持不变。还需传递原有 `SINGULARITYENV_*`/`APPTAINERENV_*` CPU、TemplateFlow 和许可环境，并核验容器 launcher 与实际子进程都为 0、完整 `validation_complete` 及所有输出检查。源码及入口改变记录到新的参照清单；不修改已运行候选或根任务 helper。
